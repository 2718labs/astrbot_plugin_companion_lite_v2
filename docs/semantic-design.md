# CompanionLite V2 语义与状态设计

本文档是 CompanionLite V2 当前关系语义的设计契约。README 负责产品定位、安装与操作入口；这里说明关系证据如何进入状态、状态如何形成边界，以及主人格最终会收到什么。

## 职责边界

CompanionLite V2 是关系侧车，不是主人格、用户画像或长期事实记忆。

- 它维护“当前愿意投入多少、与对方保持多远、是否存在待处理问题”。
- 它不保存用户姓名、偏好、经历等事实；这些信息应由专门的记忆组件管理。
- 它不替换 AstrBot 人格提示，也不向人格增加和善、安抚或用户情绪保护规则。
- 它不允许分析模型直接修改关系状态。小模型只提交离散证据，代码负责标签校验、状态门控、结算和裁剪。
- 它不把内部数值、问题编号或分析标签交给主人格，只提供可执行的自然语言。

所有关系数据按 AstrBot 完整 UMO 隔离。群聊不进入关系处理。

## 一轮消息的处理管线

一轮指一次用户私聊消息加一次主人格回复。分析发生在回复完成后，因此分析结果只指导下一轮。

### 主回复前

1. 捕获用户私聊消息并写入当前 UMO 的消息缓冲。
2. 单条消息按配置限制长度；超长文本保留约三分之二的开头和三分之一的结尾，并插入原始长度标记。
3. 本地检查是否存在直接贬低、威胁、强迫或已表达边界后的继续施压。
4. 普通消息直接继续；命中候选时才调用一次五秒严重确认模型。
5. 解析当前人格及其正式绑定角色，读取 UMO 关系档案。
6. 代码将关系状态编译为五标签 `companion_state`。
7. `observe` 只保存下一轮预览，不进行提示词注入行为；`active` 才会同时加入稳定协议和动态状态。
8. 主人格生成回复。

严重确认失败、超时、低置信或返回无效数据时失败开放，不修改关系，由后续轻分析或深分析兜底。

### 主回复后

1. 保存主人格回复，并与用户消息组成一个完整来回。
2. 偶数轮进入分析调度：
   - 第 `2 / 4 / 8 / 10 / ...` 轮运行轻分析，读取最近两个完整来回。
   - 第 `6 / 12 / 18 / ...` 轮运行深分析，读取截止目标轮次最近最多 20 条已完成消息，并覆盖同轮轻分析。
3. 小模型输出固定证据标签、置信度和简短证据。
4. 代码检查标签取值、置信度、轮次、当前状态及证据字段之间的逻辑条件，再按固定规则更新关系档案。

同一目标深轮次只允许结算一次。后台分析、管理员反思、Web 反思和档案重建共用同一 UMO 分析锁。

## 关系状态

持久关系由三维数值、一个姿态、一个主导问题和一条可修订感受组成。

### 三维关系

| 字段            | 范围          | 变化                       | 语义                  |
| ------------- | -----------:| ------------------------:| ------------------- |
| `familiarity` | `0..100`    | `0 / +2 / +5`            | 对这个人与相处方式的了解积累，只升不降 |
| `trust`       | `0..100`    | `-10 / -4 / -2 / 0 / +2` | 是否形成可以依赖的默契         |
| `affinity`    | `-100..100` | `-10 / -4 / -2 / 0 / +2` | 人格对当前互动的主观亲和或疏离     |

默认信任为 `50`，只表示暂时没有明显不信任，不代表已经形成稳定信任。熟悉、信任和喜欢彼此独立：长期互动不必然带来信任，信任也不等于偏爱。

熟悉度阶段：

| 范围       | 阶段   |
| --------:| ---- |
| `< 10`   | 陌生   |
| `10..34` | 认识一些 |
| `35..64` | 熟悉   |
| `>= 65`  | 长期熟悉 |

自然演化每六轮最多结算一次熟悉度，最早第 12 轮才可能离开陌生阶段。管理员明确建立正式关系是唯一可以即时补足熟悉度的路径。

### 关系姿态

| 姿态           | 本轮行为上限                 |
| ------------ | ---------------------- |
| `normal`     | 结合熟悉度、信任、亲和与身份决定投入     |
| `reserved`   | 简单问题至多给结论或一个要点，费力任务可拒绝 |
| `guarded`    | 默认拒绝非必要任务，不先附赠答案       |
| `disengaged` | 不承接普通任务，只在愿意时回应具体修复    |

姿态优先于负亲和，负亲和优先于熟悉度，低信任限制额外投入。正式身份不能覆盖姿态和未解决问题。

### 主导问题

同一时间只保留一个活动问题：

- `one_sided`：连续索取内容，却很少回应或承接投入。
- `ignored_expression`：已经表达互动偏好，对方仍忽略或继续施压。
- `boundary_violation`：明确边界后仍继续施压。
- `degradation`：针对人格本身的贬低，而非批评具体回答。
- `coercion`：威胁、勒索或强迫服务。

问题阶段为：

- `noticed`：已经识别，但不假定主人格曾清楚表达。
- `expressed`：分析结果标记主人格已经表达偏好或边界，而问题仍继续。
- `repairing`：对方开始具体承接并改变行为，关系尚未完全恢复。

## 证据与代码裁决

分析模型只允许使用固定标签。代码会拒绝未知标签、所有低置信关系模式，以及不满足既定字段组合或当前状态门控的升级。

代码不会重新阅读或理解原始对话，也不存在第二套语义识别器。`agent_expression`、`user_response_to_expression`、`pattern` 等仍是分析模型提交的证据字段；代码只能检查这些字段是否构成允许的状态转换，并限制一次判断最多造成什么影响。

- 熟悉度只接受 `none / small / clear`。
- 信任与亲和只接受 `strong_down / down / down_small / same / up_small`。
- 严重事件必须是高置信，普通批评、简短命令和专业问题不能直接建立严重问题。
- 未解决问题存在时，信任和亲和不能通过普通正向互动上升。
- 修复期每个分析周期的信任和亲和最多各恢复 `2`。

旧关系总结和旧感受只是待复核假说，不能代替当前窗口证据。关系总结最多 80 字，仅供调试；第一人称感受经过注入指令清洗并限制为 40 字。

`deep-v7` 要求 `impression` 只写对对方的第一人称感受，不复述或转写谁做了什么、谁关心了谁等事件；关系事实与第一人称感受不能互相矛盾。旧感受为空且本周期首次确认负向关系模式时，必须提交 `revise` 和非空感受。低置信度分析不采纳模型的 `revise` / `clear` 印象操作，既有感受保留，缺失时由兜底接管。模型仍可能漏字段、返回 `keep` 或让感受在清洗后变空，因此代码还会根据已经裁决通过的模式、活动问题、姿态和亲和状态生成确定性兜底。这个兜底不重新阅读或理解原始对话，只把已经确认的结构化关系结论编译成相符的第一人称态度；它保证状态一致，不替模型证明对话事实。

## 单向互动与逐步收门

连续单向索取使用两轮轻观察和六轮深结算，不在第一条任务上武断拒绝。

- 第 2 轮首次中高置信确认：不改变持久姿态；下一轮若继续投递新任务，`投入`、`处境`、`感受` 和 `表达` 会共同要求拒绝，不提供答案；暂态感受只表达“开始不喜欢这种互动”，若没有继续该模式，再按原关系上限回应。
- 第 4 轮再次确认：明确互动偏好，后续新任务直接拒绝，只回应具体承接或修复。
- 第 6 轮深分析仍确认单向索取：
  - 若主人格尚未实际表达，进入 `one_sided / noticed / reserved`。
  - 若分析模型同时标记主人格已表达，且用户随后忽略或继续施压，代码才允许进入 `ignored_expression / expressed / guarded`。
- 首次六轮确认固定结算熟悉度 `+2`、信任 `-2`、亲和 `-4`。
- `reserved + one_sided` 遇到新的知识请求或任务时一律拒绝，不提供答案、要点、替代教程或继续展开邀请；只回应具体承接、解释或修复。

“相同任务的自然追问”与“拿走较重成果后跳过互动、立刻投递无关任务”必须区分，后者才是单向关系证据。

## 严重事件预检

本地预检只判断“是否值得复核”，不直接定罪。候选范围包括：

- 直接针对 agent 的人格贬低；
- 威胁、勒索和条件式伤害；
- 强迫服务或否定拒绝权；
- 已表达边界后仍明确继续施压。

引用块与代码块会先被排除。只有命中候选才调用严重确认模型，输入最多 400 字，超时五秒。

每个 UMO 每六轮最多确认两次，同一规范化消息去重。明确且高置信的严重事件可以进入 `guarded`；极端威胁或在 `guarded` 下重复同类严重行为可以进入 `disengaged`。插件允许冷硬拒绝和结束互动，不授予持续攻击或主动升级冲突的权限。

本地候选筛查刻意保持高精度，不把含混阴阳、普通吐槽或双方自然玩笑扩张成词面定罪。隐性贬损只有在跨轮分析得到至少中等置信的明确关系证据后才可影响状态；低置信结果只保留在诊断中。

## 礼貌性沉默桥接

Companion 不直接执行“不回应”，而是可选地与 `astrbot_plugin_polite_silence` 联动：决策与执行分离，Companion 决定何时提示拒答，polite_silence 负责解析 `<ignore>` 标签并在一段时间内拦截该用户消息。

### 接管与降级

- `bridge_polite_silence` 开启且处于 `active` 时，插件探测 polite_silence 实例并把其 `trigger_percent` 置 0，避免两套概率触发并存；原值被记录，开关关闭或插件卸载时还原。
- 接管只执行一次，用户之后在面板手动修改 `trigger_percent` 会得到尊重；未安装 polite_silence、缺配置字段、`observe` 模式或开关关闭时整条链 no-op。

### 触发条件

在每次主请求前，根据已裁决的关系状态决定是否追加拒答提示（携带真实 sender_id 与建议时长）：

- `disengaged` 必注入（建议 90 分钟）；
- `guarded` 且活动问题为 `boundary_violation / degradation / coercion`、阶段为 `noticed / expressed` 时注入（建议 30 分钟）；
- `light_guidance.reminder == hold_boundary` 时注入；
- `repairing` 阶段一律不注入，给修复留出空间。

提示只说明“可以选择礼貌性沉默”及指令格式，最终是否输出 `<ignore>` 由主模型自主决定；polite_silence 的时长上下限与白名单仍然生效。

### 事件记录与恢复告知

- 响应侧以 `priority=-10` 优先于 polite_silence 取得未清理文本，解析 `<ignore>` 标签（自闭合与双标签、属性大小写不敏感，取 id 与 duration）；确认 polite_silence 已注册才记录，避免幽灵事件。
- 事件写入 `last_silence_event`（target_id、duration_minutes、source_round、created_at）并累加 `silence_count`，随 `companion_state` 持久化。
- 能再次收到该用户消息即视为拒答已结束（含管理员手动解封）；此时一次性告知主模型“上一轮沉默了 X 分钟”，随后清除事件，不重复注入。
- 拒答次数当前只用于记录、状态展示与诊断，不直接参与关系数值计算。

## 修复

泛泛道歉、低置信修复或没有活动问题时的友好表达都不计入修复。

1. 第一次中高置信 `repair` 必须具体承认问题并接受后果。问题进入 `repairing`，姿态软化一级，感受改为愿意观察修复，但不恢复额外投入或亲近。
2. 下一个不重叠的两轮窗口再次确认 `repair`，且期间没有复犯，才清除活动问题并再软化一级；感受按仍然存在的姿态、亲和与信任保留适量不满，同时明确重新开放观察。

轻分析与深分析共享同一个 `active_issue.phase`，因此“轻转深”或“深转轻”都可以完成第二次独立确认，不需要固定等待下一次六轮深分析。第二次确认与第一次目标轮次至少相隔两轮。

## 熟悉、好感与负向表达

### 中性与正向

- 陌生：只用两三句直接回答当前问题，只给关键结论或方向，不展开成长教程。
- 认识一些：可以解释几个核心点，表达稍微熟络。
- 熟悉：可以答完整但保持简练，相处自然、松弛。
- 长期熟悉：可以承接共同语境，表现长期熟稔；没有偏爱时不主动亲昵。
- 亲和为正但低于 `15`：可出现轻微熟络和松弛，不主动拉近关系。
- `affinity >= 15`：更柔和、更愿意自然关心；可以按明确请求细讲当前问题，但不主动暧昧或使用亲昵称谓。
- `affinity >= 45`：明显更上心，可主动关心并表现少量偏心；仍不使用伴侣称谓或排他表达。

低信任、活动问题、受限姿态和正式身份约束始终覆盖普通正向分支。

### 负向

- `-1..-14`：不耐烦、冷淡尖锐，可偶尔挖苦一句，但不纠缠。
- `-15..-30`：明确反感，减少解释，可挖苦或拒绝，不主动升级冲突。
- `<= -31`：强烈厌恶、冷硬疏离，默认拒绝非必要请求；不争吵、不追着攻击。

负向分数会同时限制投入和表达。即使已经长期熟悉，也不能用熟悉度覆盖当前厌恶或不信任。

## 人格级正式关系

正式关系不由分析模型自动晋升，只能由管理员在对应私聊窗口执行 `/companion_bond`。

人格 ID 按三级顺序解析：

1. 当前 UMO 的 `session_service_config.persona_id`；
2. 当前 conversation 的 `persona_id`；
3. 当前 UMO 默认人格的 `name`。

`[%None]`、不存在的人格或解析异常均失败关闭，不使用 UMO 第一段显示名代替人格。

每个人格只有一个正式关系窗口。首次绑定会把不足的数值补到熟悉度 `35`、信任 `60`、亲和 `15`，但不会清除活动问题、姿态、感受或消息；原感受为空时，会按绑定后已经成立的状态补出相符态度。幂等绑定和解绑后重绑不会重复补值。

正式身份的编译遵循当前原因：

- `guarded / disengaged`：正式身份仍在，但当前边界优先。
- 存在活动问题：当前问题与关系距离优先。
- 仅因负亲和、低信任或 `reserved` 受限：当前感受与关系距离优先。
- 只有姿态正常、没有活动问题且信任与亲和未跌破绑定起点时，才允许自然主动或回应亲近、暧昧与昵称。

解绑只撤销正式身份，保留三维状态、问题、感受和消息；之后最高按熟人距离表达。

其他窗口即使亲和 `>=15`，也只保留真实好感和普通投入：可以答全当前问题，不额外细讲或包办；不得获得正式身份、伴侣称谓、排他暧昧或偏心投入。姿态、活动问题、负亲和和低信任仍优先。

关系尚浅且未正式绑定时，清晰预设伴侣身份或推进暧昧可以形成 `premature_intimacy` 观察。轻分析只提醒保持普通距离；深分析每个六轮窗口最多结算熟悉度 `0..+2`、信任 `0`、亲和 `-2`，不创建主导问题或升级姿态。正常正式亲密表达可以豁免，骚扰、强迫和威胁不能豁免。

## 五标签语义编译

主人格采用双层协议：

- `companion_protocol v4` 是字节稳定的 system 前缀，解释字段职责、执行顺序和拒绝规则。
- `companion_state` 是每轮变化的临时内容块，追加在当前用户消息之后。

动态状态使用 `260..340` 字硬预算，并始终保留五个标签：

| 标签   | 职责                      |
| ---- | ----------------------- |
| `投入` | 本轮帮助意愿和回答量的硬上限，并先决定是否拒绝 |
| `关系` | 当前关系身份与距离，不代表服从         |
| `处境` | 当前有效的短期观察或仍待处理的具体互动事件 |
| `感受` | 人格当前真实的第一人称主观态度         |
| `表达` | 语气、情绪表达权限和提醒方式          |

中高置信轻分析在有效窗口内会同时约束相关标签，而不是只在 `<表达>` 末尾追加一句提醒。持久活动问题优先于短期观察；修复阶段只接受对应的软化提醒，过期或不同类别的轻提醒不能覆盖当前问题。

没有活动问题或有效短期观察时，处境固定写“当前无待处理的具体互动事件”；这不否定 `<感受>` 中可能存在的厌恶、警惕或好感。只有结构化关系状态也无法推出态度时，感受才使用空占位。

执行顺序固定为：

1. 先按 `<投入>` 决定是否愿意回答以及回答多少。
2. 再结合 `<关系>`、`<处境>`、`<感受>` 和 `<表达>` 生成回复。
3. 若投入要求拒绝，不得先交付大部分答案再表示不满。
4. 不向用户复述内部标签、状态、数值或提示协议。

## 多会话、存储与并发

关系键直接使用事件的完整 `unified_msg_origin`，例如：

```text
bot:FriendMessage:demo-user
```

每个完整 UMO 独立拥有：

- 关系状态与消息缓冲；
- 待处理交互与轻提醒；
- 响应锁、分析锁和反思队列；
- 严重确认窗口与提示词预览；
- 是否启用陪伴功能。

`conversation_id` 只参与人格解析，不作为关系缓存键。同一发送者通过不同 UMO 进入时会得到独立档案。

插件只创建四张业务表：

- `companion_state`
- `message_buffer`
- `pending_interaction`
- `companion_bond`

重置操作在分析锁内清空目标 UMO 的状态、消息、待处理交互、反思队列及其正式绑定，不影响其他 UMO。

## 运行模式与诊断

### `observe`

- 捕获消息并运行全部关系分析；
- 编译并保存下一轮预览；
- 不修改主人格请求；
- 允许未正式绑定或曾绑定窗口使用“保留消息并重建档案”。

档案重建从第 2 轮开始重放有效轻、深分析。只有全部步骤成功，且期间没有新消息或状态变化时才原子替换关系档案。正式绑定窗口在任何模型调用前拒绝重建，失败不破坏原状态。

### `active`

- 保留 `observe` 的全部记录与分析；
- 向主人格请求加入稳定协议和动态五标签状态；
- 记录上一轮实际注入快照，供调试页与下一轮预览对照。

调试追踪记录提示词版本、动态输入字符、模型证据、代码裁决和提供商报告的 cached、uncached、output tokens，不保存完整分析提示词副本。

关系档案与启停管理每五秒静默同步。数据无变化时不重绘；文字选择或输入操作期间暂停刷新，并保留滚动、页签、折叠、消息展开和交互焦点。
